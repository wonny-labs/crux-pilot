# eMMC and Reliance Edge physical gate

Issue 8 of the [eMMC design](plans/emmc-reliance-design.md) ([#256](https://github.com/wonny-labs/crux-pilot/issues/256), milestone M14). This fixes the procedure for the physical runs that the design leaves for later, so that a run starts from stated preconditions, observable outcomes and stop conditions. It follows the structure of the [microSD physical gate](microsd-physical-gate.md). **This document authorises nothing, and no hardware was touched to write it.** Every hardware step needs explicit approval for the current task; a past approval does not carry over, and approval for Stage A does not cover Stage B. Nothing here has been run, so no step below has a result.

The software evidence that precedes this gate is in the design's Verification section and under `docs/evidence/emmc-reliance/`. All of it comes from runs on Zephyr's `native_sim` board against a test-only eMMC simulator, which the author of the code under test wrote, apart from the RT1060 Rev B link checks, which run nothing. The microSD results to compare with are in [the append cuts](evidence/microsd-power-cut/README.md) and [the replace cuts](evidence/microsd-replace-cut/README.md).

## Two stages

- **Stage A: Reliance Edge on the EVKB microSD.** The adapter and the File provider do not depend on the medium, so this needs no eMMC. It uses the existing power-cut rig and the same two workloads as the FatFs runs, so the results compare directly. The disk name is `SD`, as in the microSD composition. The card is a microSD, so this says nothing about an eMMC.
- **Stage B: a board with a real eMMC.** The EVKB has none. Stage B needs a board that has one, and that board is not described in this repository: its identity, wiring and supply are preconditions of the approved task, not assumptions of this document. The EVKB overlay of the reference composition (`samples/storage_emmc/boards/mimxrt1060_evk_mimxrt1062_qspi_B.overlay`) is for linking only and describes no board. **Stage B cannot start** until the approved task has fixed, for that board, the flash backup, restore, verification and restore image of precondition 4, the power-cut mechanism and supply check of precondition 3, and the device description.

Stage A comes first. Its result decides nothing about Stage B beyond the adapter and provider behaviour on a target.

## Dependencies: what exists and what does not

The work of issues [#253](https://github.com/wonny-labs/crux-pilot/issues/253), [#254](https://github.com/wonny-labs/crux-pilot/issues/254) and [#255](https://github.com/wonny-labs/crux-pilot/issues/255) is merged as pull requests; the issues are still open. What that work provides is software evidence on `native_sim` and link-only RT1060 builds, and none of it ran on a target. On main there are the adapter, the Reliance Edge File selection (`CONFIG_CRUX_FILE_RELIANCE_EDGE`, which makes 32 the default of `SDHC_BUFFER_ALIGNMENT`), the Reliance Edge replay on `native_sim`, the reference composition `samples/storage_emmc`, a link check of it for RT1060 Rev B (`scripts/test-file-emmc-compile.sh`), and the Settings File provider. The `samples/storage_sd*` images are FatFs only. The RT1060 build of the composition is a link check on an overlay that replaces the SD disk with an MMC disk named `MMC`, exists to link only, and must not be flashed to an EVKB. The replay workloads (W1 to W4) exist only as a `native_sim` image.

**The Stage A images exist as build-only images and as a `native_sim` rehearsal, and nowhere else.** They are five scenarios of `samples/storage_reliance_sd`: the default image, the mount check (`.start`), the append image (`.append`), the replace image (`.replace`) and the format image (`.format`). Each is a link-only RT1060 Rev B Twister scenario that `scripts/test-file-emmc-compile.sh` builds and checks. The check requires the microSD disk driver, Reliance Edge, an alignment of 32, `red_format` in the format image only, and a linked size below `0x60600000`. Nothing is run. Each also builds for `native_sim` and runs there in a rehearsal on the eMMC simulator (`tests/native/reliance_stage_a`, run by `scripts/test-storage-emmc.sh`; the [test guide](../tests/README.md) states its limit). The rehearsal exercises the images' application logic, the File provider and Reliance Edge on a model of a disk. It does not exercise the SD host driver, the SD layer, a card or a power cut. **None of the images has been flashed. None has been independently reviewed for the board as precondition 6 requires**; the review of the pull request that adds them is not that review. **No card has been formatted.** No per-cut voltage reader exists in this repository. The `--cut-cmd` wrapper `scripts/power_cut.py` exists, but it has been tested only with fake commands and has never been run with a hub, a probe or a board (see "Flashing, console and cuts").

The Stage A images are not `samples/storage_emmc` with another disk name. The `prj.conf` of `samples/storage_emmc` selects the MMC disk driver and its link check refuses the SD driver, so that sample stays an MMC link check. `samples/storage_reliance_sd` has its own `prj.conf` with the microSD disk driver and the disk name `SD`; the mount point stays `/MMC:`. Its append and replace images compile the sources of `samples/storage_sd_interrupt` and `samples/storage_sd_replace` unchanged behind a shim header, so the console lines are those of the FatFs runs and the host scripts are theirs. The Stage B images are all to be built, and Stage B also needs a board description. Their existence, review and settings are preconditions below, and a step that names one waits for it.

## Rules and scope

- **Test-owned media only.** A card or device used here may be erased or left needing a reformat. Platform compositions never format (design D9): formatting is done by a test image built with the format option (`CONFIG_CRUX_FS_RELIANCE_EDGE_FORMAT`, off by default), as its own approved step, on test-owned media. On Stage A that image is the format image of `samples/storage_reliance_sd` (`CONFIG_SAMPLE_RELIANCE_SD_FORMAT=y`, which selects the formatter option). **It formats whenever its first mount fails, whatever the cause**: a card with no volume, but also an I/O error, damage, or a build whose sector offset or count differs from the one that formatted the card. It cannot tell a blank card from a damaged one. A card on which a volume mounts is left as it is and the image reports status 2. This is why the format image runs on test-owned media only, and a card whose contents matter must never meet it.
- **Test images, not for distribution.** Images that link the public Reliance Edge source are test images (design D6). Record their checksums and build settings. Do not commit them, upload them from CI or store them under `docs/evidence/`.
- **Default-off images.** As in the microSD gate, an image that touches the medium has that behaviour behind a Kconfig option that is off by default, and is flashed only for an approved run.
- **The File additions need their own approval.** The design's owner decision covers an RT1060 link of the File additions, and nothing more. If an image runs roots, stat, size, rename or listing through `crux/file.h` on a target, the task's approval must say so (design F18).
- **The alignment setting.** The design records that no board had run the `SDHC_BUFFER_ALIGNMENT` change at its writing, on FatFs or Reliance Edge. The Reliance Edge File selection makes 32 its default, a build can override it, and two checks bound it: `file_native.c` refuses a value below the data cache line size when the data cache is on, and the adapter refuses a value above its own buffer alignment of 32. A Stage A image with that selection therefore runs a value of 32 on a target with Reliance Edge for the first time, unless the value recorded in precondition 6 differs. A data fault there is a finding about that change as well as about the file system.
- **Operator-reported facts are marked as such**, unless a tool read them. Physical results are recorded apart from `native_sim`, replay, cross-build and CI results; none of those implies another.
- **The existing flash may hold another project's image.** It is backed up and restored as below, whatever the stage.

## Preconditions (record all of them before the first flash)

1. **Board.** Stage A: RT1060-EVKB Rev B, QSPI (`mimxrt1060_evk@B//qspi`), the M.2 slot state, and uSDHC1 ownership against the schematic; revision and variant are operator-reported, because the build guard checks the build target and not the board that is fitted. Stage B: the board's identity, the eMMC part number from its marking or documentation (not from software), which uSDHC instance it is on, its bus width, its signalling voltage and supply, its reset line, and the schematic page that shows these.
2. **Probe.** SEGGER J-Link PLUS, device `MIMXRT1062xxx6A`, SWD at 400 kHz, as in the microSD gate. Read-only check first: the probe is listed and the target connects (CPUID, VTref). Stage B uses the same probe settings only where the board has the same MCU variant; otherwise the approved task fixes and records them.
3. **Power, and the supply check.** On 5 November 2026 the owner reported that the EVKB is powered through J1 USB only and that J48 is not connected (operator-reported). A re-measurement run that day switched the DAPLink's hub port off. The DAPLink and its serial port disappeared, but the target reference voltage read 3.322 V after 3 seconds, so **that port did not remove target power**. No log of that reading is kept in this repository. The rule below does not depend on it. Switching a hub port off therefore does not show that the board lost power. The cause was not established, and the result differs from the 2 November run, where the same reading went to 0.000 V. Before any power-cut run, and again after anything in the setup changes (cable, hub, port, supply):
   - find the board's hub and port with `uhubctl`, name the hub (`-l <hub>`) on every command, and confirm the DAPLink is the device on that port (the port was 3 on 2 November and 4 on 3 November);
   - switch the port off and read the target voltage (VTref) after the pause that the cut will use. It must show a drop to about 0 V, and the supply of the medium (the card, or the eMMC rails on Stage B) must be shown to drop too, with the tool or instrument named;
   - switch it on and confirm the reading returns to about 3.3 V.

   **If the reading stays at its on value, the run stops and no cut is made.** A cut made without this check is not a power cut and is not recorded as one. On Stage B the board may not be powered through USB at all, so the cut mechanism is itself something the approved task has to fix and show with the same check.
4. **Flash backup and restore.** The board's flash may hold another project's image, and this procedure replaces it.
   - **Stage A values.** The QSPI chip is 8 MiB (the board's devicetree in the pinned Zephyr, `mimxrt1060_evk_mimxrt1062_qspi.dts`, an `is25wp064` of `DT_SIZE_M(8)`). The operator's experience is that J-Link reads fail from `0x60600000` on this board; no record of that is retained in this repository, so it is operator-reported and was not measured here. Back up the first 6 MiB at `0x60000000` (`savebin <file> 0x60000000 0x600000`).
   - **The upper 2 MiB is not backed up.** The range above `0x60600000` can be neither saved nor restored by this procedure. The Zephyr default `storage_partition` of this board starts at `0x620000`, which lies above the backup, so another image that keeps data there would lose it. **No image and no step may erase or program above `0x60600000`.** Check this from each image's flash and partition use before it is flashed: its linked size ends below `0x60600000`, and it uses no NVS, Settings or other storage on flash. If the other image's use of that range is not known, treat it as in use and ask the operator.
   - **Verify the backup** by reading the same range a second time to a second file and comparing the SHA-256 values. Record the value. Keep both files outside the repository. A backup of the first 6 MiB shows what those bytes were. It does not show that they are all the other image holds.
   - **Restore and read back** at the end of every run with `loadbin <file> 0x60000000`, then read the same range with `savebin` into a new file and compare its SHA-256 with the backup's. If they differ, **stop and ask**; do not reflash blindly. Until a restore has been read back, the backup is a record and not a tested restore.
   - **Stage B** has no values here. The chip, the address range, what can be read, the backup, the restore, the read-back and an inert restore image for that board are fixed by the approved task. Without them Stage B does not start.
5. **Media prepared.** Stage A: a test-owned card, its size and partition scheme. Formatting for Reliance Edge is done once by the test image with the format option. After it the card holds no FAT volume, so `fsck_msdos` and `diskutil verifyVolume` do not apply to it. The format image creates the `files` and `settings` directories after it formats, and the composition images create none. Stage B: nothing can be taken out of the board; record the device as it is, and the offset and size of the volume that the Kconfig values give.
6. **Images exist and are reviewed.** For every image flashed:
   - the image exists and has been independently reviewed against the approved task, and its source revision and SHA-256 are recorded;
   - anything it does to the medium is behind a Kconfig option that is off by default, and the build settings that turned it on are recorded;
   - `red_format` is absent from every image except a format image, which is used once, on test-owned media, as its own approved step, and a check confirms its absence in the others;
   - `CONFIG_SDHC_BUFFER_ALIGNMENT` and every configuration value, in Kconfig or in `zephyr/fs/reliance_edge/config/redconf.h` or `zephyr/fs/reliance_edge/config/redconf.c`, that the medium's format depends on are recorded (for example the block size, the name limit, the direct and indirect pointer counts, the inode and inode map settings, atomic rename and the transaction settings in `redconf.h`, and the sector size, the sector offset and count, the atomic sector write flag, the inode count and the block I/O retries in `redconf.c`). A formatted medium and the image that mounts it must use the same profile; the design records that several of these values are checked against the medium at mount. The handle count is a build setting: `REDCONF_HANDLE_COUNT` in `redconf.h` must equal `CONFIG_CRUX_FS_RELIANCE_EDGE_HANDLE_COUNT`, which a build assertion checks, and the buffer and task counts are Kconfig values. Record all of them. For each Stage B image record `CONFIG_CRUX_MMC_CACHE_FLUSH`;
   - its linked size ends below `0x60600000`, and it uses no flash storage above it.
7. **Console.** The DAPLink serial port at 115200 baud, with the speed set on the open handle, and checksummed lines accepted only when the checksum matches, as in the microSD gate. Stage B: the board's own console, named in the approved task.

## Card handling

The card stays out of the board while the other project's image is on it, during the backup, and until the first Crux flash. It goes in only with the port switched off, after a Crux image that touches no card (the restore image below) has been flashed. After that a card-touching image is flashed with the card in, because that is the run being tested. At the end of a run the card comes out with the port off, after the restore image has been flashed, and stays out of the board while the other project's image is restored. Taking the card out and putting it in needs the operator.

## Stage A steps

The [run sheet](#stage-a-run-sheet) after this list gives each step's image, build option and command shapes. The numbers of the steps are cited elsewhere and stay as they are.

1. **Backup and restore image.** With the card out, take and verify the backup of precondition 4, then flash the restore image: the microSD gate's `samples/storage_sd` with none of its options set, which touches no card. Record the command file and log, and confirm erase, program and verify report Done. Switch the port off, put the card in (see "Card handling"), and then proceed.
2. **Format, once.** Flash the format image, run it once on the test card, and record its console. Then flash the restore image again before the next step.
3. **Blank-card mount check.** Use a card that holds no volume: a separate blank card, or the card erased on the host. Take a raw digest of it on the host before it goes into the board and another after it comes out, where the host can read the raw device, and record that limit where it cannot. Flash the composition image (disk `SD`, mount `/MMC:`, no format option). A blank card must report a mount failure and the two digests must be equal, which shows the image did not write to it. A formatted card is not compared this way, because formatting and workloads change it.
4. **Mount check, formatted card.** On the formatted card with its layout in place, a normal boot reports the ready status. The statuses are those of the composition image.
5. **Append cuts.** The append workload of the FatFs run: 32-byte checksummed records, a sync after each, an acknowledgement printed only after the sync returned, cuts made as in the [append cut record](evidence/microsd-power-cut/README.md) and judged by pairing the last acknowledgement seen with the next boot's recovery report. At least 33 judged cuts, so the counts are comparable.
6. **Replace cuts.** The replace workload: write a temporary file, sync, close, rename it onto the existing file through the VFS. The classes are those of the [replace cut record](evidence/microsd-replace-cut/README.md). At least 100 judged cuts.
7. **Restore before the card is handled.** Flash the restore image, switch the port off, and only then take the card out. Boots of a card-writing image while the card was being moved were unobserved in the FatFs runs, and this order prevents that.
8. **Verify.** With the card out, read what the host can read. A card cannot be checked on the host with `fsck` while it is in the board, and a Reliance Edge volume has no host tool in this procedure. The board's own recovery report on the boots of the cut series is the main check. A host-side reader of the layout is a separate item and needs its own approval. Do not repair or reformat a card without approval, and keep it unchanged as evidence until the results are reviewed. The card stays out of the board (see "Card handling").
9. **Restore the flash.** With the card out, switch the port on, restore the backup, read it back and compare as in precondition 4, and switch the port off. The card stays out.

**What to compare with the FatFs results.** The FatFs record shows, for the append test, 33 judged cuts with no acknowledged record lost, no torn tail, no damaged record and no mount failure, and for the replace test, 100 judged cuts of which 29 left no settings file and a complete newer temporary, with a clean check before and 40 orphaned clusters after. Those are the observed outcomes of one board and one card, not rates. A Reliance Edge result is compared outcome by outcome, and the cut method, timing and card are recorded so that a difference can be attributed. The design documents an atomic replace on this file system (design F9). The replay asserts it on the simulator's model, for W1 to W3 on `red-fix`, W2 being the workload that creates a temporary file, syncs and renames it (see [the Reliance Edge replay record](evidence/emmc-reliance/replay-reliance/README.md)), so Stage A would be the first test of it on a card, and it is recorded, not asserted. Zero cases of a class in 100 cuts is bounded only by the upper limit of the 95% Wilson interval, about 4%, for a loop under that cut method. In 33 cuts the same limit is about 10%. A record must not read either as absence.

A value marked as an example comes from an earlier run or from a script default and is not a requirement. ### The images

| Image | Build option | What it does to the card | Console |
| --- | --- | --- | --- |

- `emmc_storage_start: <n>` and `sd_storage_start: <n>` use one numbering: 0 ready, 1 no media (the disk did not initialise), 2 mount failed (the file system's mount returned an error; the image never formats), 3 layout missing (the volume mounted and a required directory is absent; none is created, and the volume is unmounted again), 4 bind failed (the volume mounted with its layout, the File root did not bind, and the volume is unmounted again). Status 2 is the expected result on a blank card, but a mount can also fail on a card that holds a volume (an I/O error, damage, a build with a different sector range). Other values are in `samples/storage_emmc/emmc_storage.h`.
- **The append and replace images print `sd_storage_start: <n>` as well**, because they reuse the FatFs mains, although they call the Reliance Edge mount helper. The line is expected. It is not an error, and both host scripts already read it (`start_status` in their results). A value other than 0 means that the workload did not start (`main` returns): with 1 or 2 the volume did not mount, with 3 it mounted without the layout, with 4 the File root did not bind. Each is a stop condition (see the stop conditions below), unless it is the state that the step tests.
- `reliance_format: <n>`: 0 formatted and both directories created, 1 no media, 2 a volume mounted and nothing was formatted, 3 the format failed, 4 the new volume did not mount, 5 a directory was not created or the final unmount failed. The image prints it once and returns. Record any value other than 0 or 2 and stop. Do not reboot the image to run it again; flash the restore image.
- The options exclude each other. When two are given, Kconfig drops one of them with only a warning, and the build goes on. Before flashing, read the build's `<build-dir>/zephyr/.config` and check that exactly the one intended option is `y`, and that `CONFIG_CRUX_FS_RELIANCE_EDGE_FORMAT` is `y` in the format image and absent or `n` in every other image. Record the lines.

Replace the option as in the table, and leave out everything after `--` for the default image. The qualifier is the one that the link check uses (`mimxrt1060_evk@B/mimxrt1062/qspi`); the microSD records write the same target as `mimxrt1060_evk@B//qspi`. All of these are **test images, not for distribution**: do not commit, upload or store them, and put the SHA-256 of each `zephyr.elf`, with the source revision and the `.config` lines above, in the log of the run (precondition 6).

### Flashing, console and cuts

- **Flash** each image as in step 1 of the microSD gate (J-Link Commander, command file and log recorded, erase, program and verify Done). Precondition 4 forbids any write above `0x60600000`.
- **Console:** the DAPLink serial port, 115200 baud, as in precondition 7. The host scripts open it with the speed set on the open handle and accept a checksummed line only when the checksum matches.
- **Hub and port:** list the hubs with `uhubctl`, name the hub, find the port with the DAPLink on it, and run the supply check of precondition 3 for that hub and port on the day. Use that hub and port and no earlier value (it was port 3 on 2 November and port 4 on 3 November).
- **Cut and restore:** `uhubctl -l <hub> -p <port> -a off -f`, then `uhubctl -l <hub> -p <port> -a on`. Both commands name the hub.
- **Each cut pause is 3 s or less.** The pause is the whole time the port is off. A session of this work observed, with `uhubctl` and the probe, that the supply of this bench came back about 4.4 s after a port cut on 7 November 2026. The log of that observation is outside this repository, so the figure is reported here and not shown, and the cause was not established. A longer pause could therefore be a cut that did not hold for the time recorded.
- **In both host scripts the port is off for** the rest of the cut command after it has switched the port off, plus the wait of `--off-seconds` (which can overrun by up to about 0.2 s, the retry interval of the console read while the serial port is absent, and by up to 0.1 s, its read timeout, while the port is present), plus the start-up latency of the restore command. **That sum must be 3 s or less.** `--off-seconds` is therefore not the pause, and `--off-seconds 3` with a wrapper would exceed it.
- **The target voltage is read at about 0 V at the end of the pause of every cut**, as precondition 3 reads it after the pause that the cut uses: the 5 November reading was 3.322 V at 3 s, and a supply can return early, so a reading straight after the off command would miss that. The host scripts read no voltage, and the FatFs runs checked the supply before the series and not at each cut. For Stage A the `--cut-cmd` is `scripts/power_cut.py`, called with `--off-cmd` (the command that switches the port off), `--read-cmd` (the reader of precondition 3, which prints a whole number of millivolts on its last line), `--pause` (seconds, counted from the return of the off command), `--max-mv`, `--read-timeout` and `--log`; every option is required, so that no limit or timing is chosen silently, and `--pause` and `--read-timeout` are finite and at most 60 s. Both commands run without a shell, so no pipe, redirection or `~` works in them, and the host script runs the whole `--cut-cmd` string through its own shell, so the wrapper's options need nested quoting there (`tests/power_cut` covers one such call). It runs the off command, waits the pause, runs the reader at the end of that wait, and exits 0 only when the reading is at or below `--max-mv`. Exit 1 means the supply was still present, 3 that the off command failed (the reader is then not run), 4 that the reading failed (a non-zero reader status, an unreadable line or a run longer than `--read-timeout`, never counted as a low reading) 5 that the log could not be written and 6 that an unexpected error followed the start of the off command (the log then says `wrapper_error`), so that 1 means only a reading above the limit; each stops the series, as in the next item. Usage errors exit 2 before any command has run. The rest of the cut command after the port is off is at least the pause plus the read latency (the pause counts from the return of the off command, so the tail of that command, the log write and the process exit come on top), and all of it counts in the 3 s rule above. `--off-seconds` is set near 0 so that the wait is not counted twice. The wrapper appends one JSON line per cut to its log, with UTC and monotonic times of the off command, its return and the reading, the latency of the reading, its value and the verdict; the restore command may be a wrapper that logs the time at which it starts, so that the actual off time of each cut is recorded and not assumed. The approved task still has to choose the reader and `--max-mv`, and to measure the reader's latency on the bench (a probe tool that starts slowly may not fit the 3 s rule, and J-Link Commander updated the probe's firmware on a start recorded in `baseline.md`, so using it as the reader is a decision of the task and not a default). `tests/power_cut` runs the wrapper against fake commands (`python3 -m unittest tests/power_cut/test_power_cut.py`); no CI job runs it.
- **A failing wrapper stops the series.** Both scripts run their commands with `check=True`, so a non-zero exit raises `CalledProcessError`, the script ends without writing `--out`, and the restore command does not run: the port stays off. What is kept is the console log (`--log`, written line by line), the standard output of the script (one JSON line per recorded cycle, judged or not, printed as it happens) and the wrapper's own log. The operator then switches the port on (the card-writing image boots once more, with the card in; capture that boot and record it), flashes the restore image, switches the port off and records the state, as in the stop conditions, before anything else. If the reading does not drop, no further cut is made (precondition 3).
- **A non-zero start status does not stop a series.** The host scripts do not read it as a stop: the image's `main` returns, the script records `no_recovery_report` (append) or `no_report` (replace) for the cycle and keeps cutting. The operator watches the console and stops the series. An interrupt writes no `--out` either, so keep the log and the standard output and then follow the recovery steps of the failing-wrapper bullet above.

### By step

1. **Backup and restore image.** Build the restore image (above), then follow the step as written. The image touches no card.
2. **Format, once.** Build the format image. With the card in, flash it, run it once, and record its console and its single line `reliance_format: <n>`. Then flash the restore image again. The card must be test-owned media (see "Rules and scope").
3. **Blank-card mount check.** Build the mount-check image. The raw digests and the unchanged-card comparison are as in the step. The image is written to print `emmc_storage_start: 2` on a blank card. A `1` means the disk did not initialise, which is a different finding.
4. **Mount check, formatted card.** The same mount-check image as step 3, with no new build. It is written to print `emmc_storage_start: 0` on a card that the format image formatted.
5. **Append cuts.** Build the append image, flash it, and run the host driver of the FatFs append runs:

   ```sh
   python3 samples/storage_sd_interrupt/host/interrupt_capture.py --port <serial-port> \
       --cycles <cycles> --cut-cmd '<wrapper>' --restore-cmd 'uhubctl -l <hub> -p <port> -a on' \
       --off-seconds <off-seconds> --min-run 2 --max-run 6 --boot-timeout 25 --seed <seed> \
       --log <console-log> --out <results-json> > <stdout-log> 2>&1
   ```

   Only `--port` is required, and a cut series needs both `--cut-cmd` and `--restore-cmd`. `--baud` defaults to 115200. `--off-seconds` is not the pause: the FatFs runs used 3 with a plain `uhubctl` cut, and here it is set with the wrapper's time and the restore latency so that the sum of "Flashing, console and cuts" is 3 s or less. `<stdout-log>` and the other log paths are outside the repository. `--min-run 2 --max-run 6` and `--boot-timeout 25` are the values of the FatFs cuts; `--seed` is any value that the record states (the FatFs runs used 21 and 22). `--cycles` counts cycles, not judged cuts: the FatFs record used 30 cycles of 2 to 6 s and 3 cycles of 60 to 90 s (`--min-run 60 --max-run 90`) for 33 judged cuts, as examples. Stage A needs at least 33 judged cuts, so set `--cycles` to allow for cycles that are not judged, and run a further series if the `judged` count of the summary falls short. Do not use `--cycle-cmd`: a probe reset restarts the CPU only and is not a power cut. Do not use `--observe` for these cuts either: it records while the board is restarted by hand, so it makes no scripted cut and has no per-cut supply check. Compare as in "What to compare with the FatFs results".
6. **Replace cuts.** Build the replace image, flash it, and run the host driver of the FatFs replace runs:

   ```sh
   python3 samples/storage_sd_replace/host/replace_capture.py --port <serial-port> \
       --cycles <cycles> --cut-cmd '<wrapper>' --restore-cmd 'uhubctl -l <hub> -p <port> -a on' \
       --off-seconds <off-seconds> --min-run 0.5 --max-run 4 --boot-timeout 25 --seed <seed> \
       --log <console-log> --out <results-json> > <stdout-log> 2>&1
   ```

   The notes of step 5 apply to the options that the two scripts share, with `--min-run 0.5 --max-run 4` here; `replace_capture.py` has no `--observe`, and its `--cycle-cmd` is excluded for the same reason. `--cycles 100`, `--min-run 0.5 --max-run 4` and `--seed 31` are the values of the FatFs run, and the script's defaults for `--cycles`, `--min-run` and `--max-run` are the same. Stage A needs at least 100 judged cuts, counted from the `judged` field of the summary, with a further series if it falls short. **This step is evidence for the atomic-replace question**: the [File service assessment](emmc-reliance-file-service-assessment.md) (issue [#257](https://github.com/wonny-labs/crux-pilot/issues/257)) names this step, with Stage B items 4 and 7, as "the evidence that decides" whether File should offer an atomic replace. That decision is the owner's and the assessment takes none. The step keeps its number, and the record says which outcomes it found and which cut method it used.
7. **Restore before the card is handled.** Flash the restore image (built as in step 1), switch the port off, and only then take the card out.
8. **Verify.** No command is added here. The host reads what it can, the board's own report on the boots of the cut series is the main check, and the card is not repaired or reformatted.
9. **Restore the flash.** As in precondition 4.

Whatever the image, a step stops at the stop conditions below, and the restore image goes on first.

## Stage B steps

Each item is a separate measurement. A device that reports no cache makes the cache items "not applicable, no cache reported", not passed.

1. **Device identity.** Manufacturer, product name and revision as the stack reads them from the register set, capacity and sector count, the EXT_CSD revision and the cache size it reports. How the values are read (stack debug logging or a test image) is fixed in the approved task and recorded. A field that was not read is recorded as unknown, never as zero. The device serial number and anything that identifies a product stay out of the public record and are kept privately.
2. **Cache report.** Whether the device reports a volatile cache, its size, and whether `mmc_card_init` turned it on (design F2). Record the same for the image with `CONFIG_CRUX_MMC_CACHE_FLUSH` on. An image with it off cannot be a Reliance Edge image on a target: the adapter's guard refuses Reliance Edge on an MMC disk without that option, and `CRUX_EMMC_FLUSH_CONTROL` is honoured only on `native_sim` (design D3). Such a comparison needs a design change, or an image without Reliance Edge, and its own approval.
3. **Flush behaviour.** With the correction on and a cache present: whether `DISK_IOCTL_CTRL_SYNC` sends the flush, whether the device accepts it and what status it reports afterwards, and how long the busy period is. The simulator's status bit clears on read as Linux documents (F4); the device may differ and that is what this item reads. A flush the device rejects, or a busy period past `CONFIG_SD_DATA_TIMEOUT`, must reach the caller as an error. Linux allows 30 s and Zephyr defaults to 10 s, so record whether the default was enough.
4. **Flush latency and its effect on other threads.** The time a sync and a commit take (a commit flushes twice), under no load and under write load, with the worst case and its spread, not only an average. The flush poll and `sdmmc_wait_ready` busy-wait in the calling thread (design, Risks). Run a periodic thread of higher priority than the File caller and record its wake-up delay while the File caller syncs, and record whether a lower priority thread is starved. Do not run the File caller at a high priority to mask the result.
5. **DMA and data cache against SDRAM.** The image runs from SDRAM with the data cache on, and the driver uses DMA with a non-cached descriptor table. Read into targets that are line-aligned and into targets that share a line with another object, with a canary beside each, in SDRAM and in any other region the composition uses. Record whether a neighbour was damaged and whether the bounce path ran (design F17). A pattern written and read back through the file system, at several sizes, shows corruption that a single transfer would not. A result applies to the placement tested.
6. **Initialisation at the board's bus width and voltage.** Whether `sd_init` succeeds with the board's actual bus width and signalling voltage, and which bus width, timing mode and clock the stack ended on. If it fails, record the failing step and the status. HS200 and HS400 are outside the design, so the mode reached is recorded and is not qualified.
7. **Power cuts during the replay workloads.** W1, W2, W3 and W4 of the replay (W4 saves Settings; see [the W4 record](evidence/emmc-reliance/replay-settings/README.md)), run on the board by images that do not exist yet (the workloads exist only as a `native_sim` image), with the supply check of precondition 3 passed for this board first. The invariants are those of the replay, checked after each cut by the board on its next boot: I1, the volume mounts without formatting; I2, acknowledged data is intact; I3, a replaced file is the complete old or new version; I4, untouched files are unchanged; I5, the volume accepts a new write, sync and remount. Cuts are made at times spread across the workload, because a cut cannot be aimed at a flush from outside; the position of each cut relative to the last acknowledgement is recorded, and the acknowledgement count is a lower bound. If the device reports a cache, run with the correction on. A run with it off is the comparison described in item 2, and carries the same conditions: it needs a design change or an image without Reliance Edge, its own approval, and test-owned media, because it exists to lose data. The replay controls (flush, barrier, early acknowledgement, damaged image) are not repeated here.

The order is items 1 to 6 before 7, so that a cut run starts from a device whose identity, flush behaviour and initialisation are known.

## Stop and recovery conditions

Stop and do not continue when: the J-Link cannot connect, or CPUID or VTref differ from the recorded values; a flash does not report Done and verify; the two reads of the backup differ; the SHA-256 of the read-back after a restore differs from the backup's; an image would erase or program above `0x60600000`, or its use of flash there is not known; **the supply check does not show the target and medium supply dropping to about 0 V**, or a cut is requested without it; the DAPLink is not on the port being switched; the medium does not mount for a reason other than the state being tested, or it mounts without the `files` and `settings` layout or the File root does not bind (status 3 or 4 of the Stage A images) where that is not the state being tested; a result is damaged or missing in a way the test does not expect; the format image would run on media that is not recorded as test-owned; a flush or a transfer fails in a way that corrupts the volume beyond what the test expects; a neighbour object is damaged in the DMA check; any step needs an action that was not approved. Then: flash the restore image, switch the port off, record what happened and ask. If that flash itself fails, leave the port off, do not move the card, and ask. A medium that stops mounting is a result, not something to repair silently.

## What only the board can answer

- Whether a real device reports a cache, how large, and whether it accepts and honours the flush command.
- How long a flush takes on that device, and what a sync and a commit do to the timing of other threads.
- Whether DMA, the data cache and the bounce path keep neighbouring memory intact on the target, from SDRAM.
- Whether `sd_init` succeeds at the board's bus width and voltage, and which mode the stack reaches.
- What a real device, with its own controller, does to acknowledged and unacknowledged data on a real loss of power, including damage outside the write being made.
- Whether the target supply really drops in a cut, which depends on the board and the setup.
- Reliance Edge on a card, in a cut, against the FatFs outcomes (Stage A).

## What the simulator, the replay and the link cannot show

The eMMC simulator is a model written from the needs of the Zephyr MMC stack, so a result shows how the stack behaves against that model, not how a device behaves. The replay shows the invariants under the cut models it defines, and it does not model a controller's own translation layer or sector damage outside the write in progress. The RAM-disk runs show adapter behaviour and the process-restart runs show acknowledged data surviving an exit, which is not a loss of power. The cross-build and link of the composition show that the code builds and what it costs, and nothing about it at run time, about timing, or about DMA. Passing one layer implies nothing about the next.

## What every record must contain

Tested revision and image checksums, probe and board facts with their source (read by a tool or reported by the operator), the approval for the task, commands and their logs, the supply check and its readings for every cut series, the flash backup and restore hashes, raw results including failures and unobserved boots, what the run shows and does not show, and the cleanup state of the board and the media. Put it under `docs/evidence/` with the raw files and without images, and have it independently reviewed. Report skipped and blocked items as skipped and blocked.
