Issue [#257](https://github.com/wonny-labs/crux-pilot/issues/257), item 9 of the [eMMC design](plans/emmc-reliance-design.md). **This document authorises nothing: no implementation, no dependency adoption, no hardware operation and no merge.** It changes no source, script, test or evidence file, and it takes no decision. By the owner's decision of 4 November 2026 (session, recorded in the design) the File contract stays as it is, and whether File should offer atomic replace is reconsidered after physical evidence. The recommendation below is input to that reconsideration. It needs the owner's decision and the physical evidence of Stage A and Stage B of the eMMC physical gate (`docs/emmc-reliance-physical-gate.md`, issue [#256](https://github.com/wonny-labs/crux-pilot/issues/256), Draft pull request #312, not on `main` at the baseline below).

## Summary

1. **[O] Both components are written against the File contract. Neither calls a FatFs function or names a FatFs type** (one comment in the service mentions FatFs, `FS:1621`). The FatFs-specific code is in the provider (`FN`), and on Reliance Edge it is compiled out (`FN:40-43`). The dependencies on FatFs are therefore in the designs of the two components, not in their calls. The table below names 20.
2. **[O] Neither component has run on this file system, and nothing in the repository shows that either has been built with it.** Nothing is known to fail, and nothing is known to work. Everything the table calls "none" is an inference from the contract and the adapter tests, not a run.
3. **[I] The largest differences are not about atomicity.** They are the thread limit of the adapter (row 18), recovery after a media error (row 17), and what a sync and a close now cost (rows 6 and 20). The thread limit can make `crux_credential_start` read `UNUSABLE` and a File service area read `ERR_IO` until a reset.
4. **[I] The File service's replacement protocol still has its window on Reliance Edge**, because it removes and then renames although the file system could replace in one step (rows 2 to 4). Its start-up recovery covers the window in the model. One recovery state has no repair route on a Reliance Edge volume (row 4).
5. **[U] Four behaviours of the file system matter to the credential store and the service and are not shown by anything here:** whether an in-place overwrite needs free blocks (row 10), whether zeroing a file leaves the old bytes behind (row 12), whether a close with nothing to save commits (row 14), and what an unlink during a listing does (row 15).
6. **[R] On atomic replace, keep the contract as it is until Stage A has run. Then, if it shows no missing or mixed destination, adopt a capability-specific replace that a provider offers only when it can honour it** (option 3 below).

## What the two components ask of File

**File service** (`components/file_service`). Uses `crux_file_open_at` in all three modes, `read`, `write`, `seek`, `size`, `sync`, `close`, `stat`, `remove_at`, `rename` and the listing calls. Managed uploads write a temporary `.crux-up-N`, then commit by a sidecar `.crux-co-N`, the removal of the target and a rename (`FS:1558-1634`). It rebuilds its counters by scanning each area at start and repairs a cut commit before any client can call (`FS:651-702`, `FS:752-769`). Its own design says that replacement is not atomic across power loss ([service contract](file-service-contract.md), "Commit and power loss").

**Credential store** (`components/credential`). Two slot files, `store.img` of 16 KiB each, in two File roots (`CS:12`, `CS:516-554`). It uses `stat`, `open` in all three modes, `read`, `write`, `seek` to 0, `sync`, `close` and `remove_at`. **It never renames and never lists** (no `rename` appears under `components/credential`). A save overwrites the inactive slot in place with one write and a sync, so that a cut leaves the old image, the new one, or a slot that the tag rejects (`CS:250-289`, [credential store](credential-store.md), "Saving").

### Paragraphs on the non-trivial rows

**Rows 2 to 4: the same sequence, a different cost.** [O] The sequence at `FS:1610-1627` is the same on both file systems. [O] On FatFs the target is gone from the moment the removal returns until the rename returns, and the replace cuts show that the window is real on one card. [I] On Reliance Edge the sequence is the same, but the file system could have replaced the target in one transaction. The File contract refuses an existing destination, which is right for FatFs and was decided on 4 November 2026 to stay. Row 4 is the part that a different file system changes: the "same size" recovery row exists for a FatFs hazard that this file system does not have, and the repair that row waits for does not exist for this file system.

**Row 6: what a sync is worth.** [I] On FatFs a sync is `f_sync`, which writes the file's data and its directory entry (not re-read here). [I] On Reliance Edge it is a volume transaction. That is better for the store: the credential store's sync after a full-slot write, and again after the header write on a first save, each become a transaction with a barrier on both sides. [I] It is also slower, and it makes the store lock and the File lock longer. Row 20 is where that is counted.

**Row 10 and row 12: two properties of the credential store that rest on in-place writes.** [O] The store's design says that after the first save "a save allocates nothing" and that erase overwrites the file in place (`CS:250-289`, `CS:821-850`). [O] Neither statement is a File contract promise. They are consequences of FatFs. [I] A file system that always holds a complete committed state (design, line 385) has to keep the old blocks until the next commit, which suggests that an overwrite takes new blocks. No test here shows it and the Reliance Edge source was not re-read, so it stays [U] for both rows. Both are answered by tests on the simulator without hardware (see the follow-up list).

**Row 17: recovery is the composition's, and the two components make it harder.** [O] The design's rule is that one media error stops writes until a remount and the composition does not remount by itself (design, lines 468-469). [O] The unmount of Reliance Edge refuses while any handle is open (`FR:369-381`). [O] The service has no call to close all transfers and its counters are filled once, at start. [I] After a media error the practical recovery for a composition that runs the service is a reset, and for the credential store a close of the store's own operations followed by a remount, since the store re-reads the active slot on every operation. This is a design question for the composition and not a defect, but nothing records it yet.

**Row 18: the thread limit.** [O] The adapter cannot free a slot when a thread exits, so a composition that creates short-lived threads which call File uses the slots up over time. [O] Slots belong to the thread object's identifier, so a thread that is created again in the same object may keep its slot. I did not check which of the composition's threads do that. [I] The credential store is the more fragile caller, because a failed first read at start makes it `UNUSABLE`, which only a reset clears.

### Checked, with nothing to report

[O] Seek to end-of-file and the size by seek (`FN:307-334`, `FN:386-406`) work through the adapter (`FR:1639`). A directory is `NOT_FOUND` to `stat` (`FN:379`), and listing skips directories and foreign names (`FR:1718`). A missing file gives `NOT_FOUND` (`FR:1663`). The handle pools are covered by a build check, 4 files and 2 listings against 8 handles by default (`FN:65-67`). The Reliance Edge profile has no timestamps (`RC:73`), and File has none (decision F6). The FatFs range check named in the credential limits table (`credential-store.md:243`) is a FatFs-only item by its description, and I did not assess it. The maximum file size of this profile was not checked. The service limits files to `INT32_MAX` (`FS:707-708`).

## Atomic replace through File

### The known gap

[O] `crux_file_rename` refuses an existing destination of any type (`FC:272-287`, `FN:425-436`). [O] The File service replaces a file by removing the target and then renaming the temporary (`FS:1610-1627`). [O] Atomic replace is reachable only through the VFS, where Reliance Edge's `rename` replaces (`AD:505-511`, `RC:35`) and Zephyr's FatFs `rename` removes the destination first. [O] The Linux provider's `renameat` replaces its destination too, and the provider checks first for the same reason (`components/file/ports/linux/file_linux.c:226-244`). [O] The replay's W2 calls the VFS rename directly (`tests/native/emmc_powercut/workloads.c:300-309`), and W4 saves through the Settings File backend, which renames through the VFS. That is why the replay can show atomic replace on this file system and says nothing about File. [O] The credential store does not rename.

### Recommendation

**[R] Option 3, adopted only after the evidence below, and option 1 in the meantime.** Nothing changes now.

Why option 3, if the evidence allows it:

1. [I] The service is a real consumer that needs replacement, and `AGENTS.md` asks to evaluate a narrow, capability-specific interface where an actual portable consumer needs one. No other consumer needs it today, and the credential store avoids rename on purpose.
2. [I] Only providers whose file system can replace atomically can honour it. FatFs cannot, and the contract should not promise what its provider cannot do. Option 2 would put a name on it that means different things.
3. [I] It removes the costs that are specific to Reliance Edge: seven transactions per upload, the sidecar and its recovery on that path, and the held name with no repair route.
4. [I] It does not touch FatFs or the microSD profile, which stay as the evaluation profile (design D7).

Why not now: [O] nothing physical exists for Reliance Edge, and a contract sentence that promises atomic replace needs physical evidence, as the File contract and the service contract already require for cuts. The owner's decision of 4 November 2026 says the same.

**The evidence that decides it** is in the draft physical gate (`docs/emmc-reliance-physical-gate.md`, Draft pull request #312, which may change):

- **Stage A, step 6 of the draft.** Replace cuts through the VFS rename on Reliance Edge on the EVKB microSD, at least 100 judged cuts, compared outcome by outcome with the FatFs record above. The gate states that zero cases in 100 bounds the rate only to about 4% at 95% and must not be read as absence.
- **Stage B, item 7 of the draft.** W2 and W4 on a board with a real eMMC.
- **Stage B, item 4 of the draft.** Flush latency, which prices the seven transactions.
- **Not in the gate and proposed here:** a run of the File-level sequences (remove then rename, and the service's commit) next to the VFS rename on each provider that would claim atomicity. The service contract already says that physical cuts during a rename and commit need their own approval.

**What would change my mind:**

- Any replace cut on Reliance Edge, in Stage A or Stage B, that leaves the destination missing or mixed. Then no provider can honour option 3. I would recommend option 1, with option 4 for the same-size state, and report the finding against design F9.
- A measured commit cost that is small next to what an upload takes, together with the owner's preference for one code path. Then option 1.
- The owner deciding that the service is not supported on FatFs. Then option 3 becomes an operation every supported provider must offer, and the second path goes.
- Software runs from the follow-up list showing that the service's recovery handles every state on a Reliance Edge model, including the same-size state. That weakens the case but does not remove the cost of the transactions.
- A second consumer that needs replace. That strengthens the case.

This recommendation needs the owner's decision. It is not a decision, and it does not authorise Stage A, Stage B or any change to the File contract or code.
