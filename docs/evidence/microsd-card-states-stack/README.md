# microSD card states, stack high-water mark and card removal — 3 November 2026

Physical-board evidence for items of [#14](https://github.com/wonny-labs/crux-pilot/issues/14) acceptance criterion 2 that earlier runs left open: how the composition behaves on a **blank** card and on a **wrong-layout** card, the **stack high-water mark**, and what happens when the card is **removed** while mounted. Gate: [microsd-physical-gate.md](../../microsd-physical-gate.md). Same board as the [first card runs](../microsd-physical/README.md). **One board, one card, one run each. This does not qualify the card, the board or the stack for any other configuration.**

## Results
| Card state (prepared on the host) | Console | Meaning |
| --- | --- | --- |
| **Blank**: no partition table, no FAT volume | `sd_storage_start: 2` | `SD_STORAGE_MOUNT_FAILED`: the disk initialised, there was no volume to mount, nothing was formatted |
| **Wrong layout**: FAT32 (MBR), no `files`, no `settings` | `sd_storage_start: 3` | `SD_STORAGE_LAYOUT_MISSING`: the volume mounted, the missing directories were detected, none was created |
| **Provisioned**: FAT32 with `files` and `settings` | `sd_storage_start: 0` | `SD_STORAGE_READY`, then the stack probe ran |

After each run the card went back to the host ([host-verification.txt](host-verification.txt)): the blank card still showed no partition map and no file system; the wrong-layout card had no `files` or `settings` and `fsck_msdos -n` exited 0. Both images only mount and look at the directories.

### Stack probe ([console](stack-console.log))
The probe mounted the card, ran the file check and the FatFs workload (create, 64 KiB write, sync, read back, rename, stat, list, remove) twice, both with result 0, then printed the thread analyzer report once:

| Thread | Stack | Used (high-water) | Unused |
| --- | --- | --- | --- |
| main (4096 B, `CONFIG_MAIN_STACK_SIZE`) | 4096 B | 2264 B (55 %) | **1832 B** |
| ISR0 (interrupt stack) | 2048 B | 240 B (11 %) | 1808 B |
| idle | 320 B | 64 B (20 %) | 256 B |

The workload and file check ran in `main`, which is what the 4096 B choice has to cover; the probe also runs the thread analyzer and its output in `main`, so the 2264 B may include the analyzer's own frames and errs on the high side. Afterwards `fsck_msdos -n` exited 0, `files` held `bootcount` (value 2) and `pattern` (byte-identical to `pattern.expected` of the earlier runs, full SHA-256 in host-verification.txt), and `settings` was empty (the workload's temporary files were gone).

### Card removal ([attempt 3 console](removal-attempt3-console.log))
The log starts at OP 400 (the capture began after the board had been running for about 80 s) and shows `state=0` with all codes 0 up to OP 600; operations 1-375 are inferred from `failures=0` at OP 400. At **OP 613** the probe printed `state=1` (LOST), `failures=1`, `codes=-8,0,0,0`: the `open` returned `CRUX_FILE_ERR_IO` (-8), the others 0. The log holds 73 `state=1` lines in all, this first one included: the first has `remount=0` (the field is still 0 from the probe's initialisation: the probe discards the result of the unmount), and the other 72 have `remount=-5` (`-EIO`), one attempt per second until the capture was stopped. A `-5` rather than `-120` (`-EALREADY`) implies the unmount itself succeeded. **`state=2` and `recoveries` never appeared:** the volume did not come back after the card was re-seated. The board did not hang or fault: it kept printing every second. The failure appeared between the OP 600 and OP 625 print points, consistent with the operator's reply at 12:54 UTC, but the console has no timestamps, so the moment of removal was not matched to the log.

The control showed the same card seated and mountable after a re-flash of `sd-start` and a reset (`sd_storage_start: 0`), so the failed remounts were not caused by an absent or damaged card. After the run the card went back to the host: `fsck_msdos -n` exited 0, `files` held `bootcount` (2), `pattern` (identical) and `probe` (32 bytes of 0x00, the probe's record), `settings` was empty ([host-verification.txt](host-verification.txt)).

## What this shows
- On this board and card, a blank card and a card with the wrong layout both fail closed with the documented codes, and the firmware neither formats nor creates a directory.
- With the card removed while the composition was mounted, the firmware reported `CRUX_FILE_ERR_IO` and did not hang; after the card was re-seated the application unmount and remount (`sd_storage_stop` then `sd_storage_remount`, retried every second) did **not** bring the volume back without a reset, which matches the documented policy "a card swap needs a reboot".
- The main stack of this composition used 2264 B at the deepest FatFs path the probe exercises, leaving 1832 B of the 4096 B, so the earlier "no measured margin" now has one measurement.

## What it does not show
- One run per state. The blank check is a `diskutil` layout check, not a sector-level comparison. A raw read needs root; the operator ran root commands for the backup, but a before/after image of the blank and wrong-layout cards was not taken: it would have needed the password for each read and about 1.9 GB of free disk (1.6 GiB were free), and the first-MiB hash that was offered as a cheaper check was not chosen. The card was made blank by a `zeroDisk` that was interrupted, so bytes beyond the first sectors may be old data. macOS touched `.fseventsd` when it auto-mounted the wrong-layout card, so the "unchanged" evidence for that card is the absent directories and the clean fsck.
- The images for the first two states are the 2 November build (the exercised source is unchanged, see above), and the stack image is the build before the wording fixes.
- The stack figure is for this composition with the file check and the workload only: no Settings backend, networking or other threads' use. ISR0 includes early boot on the same stack, so it overstates interrupt use. The analyzer listed only `idle`, `main` and `ISR0`.
- Not run: another card, SD errors and timing, the recovery step (`sd_settings_recover`) on the board (no image calls it). uSDHC1 ownership is unchecked (see Setup); the empty M.2 slot is operator-reported, so these runs say nothing about a board with a module fitted.

### Limits of the removal run
One removal, one card, one board. The result does not separate "the SD driver cannot recover" from "this composition never re-initialises the card": the remount path does not force a new card initialisation, and the source suggests the disk reference count never returns to zero, so only the application-level recovery was tested, and a forced driver de-initialisation was not tried. The moment of removal was not matched to the log (no timestamps), and the re-seating is operator-reported (the control shows the card present afterwards). Two earlier attempts gave no result and at least one (attempt 2, probably attempt 1) involved a power-cable removal that reset the board. Removing a card during writes was not tested for data loss beyond the clean `fsck` and the intact files.

## Cleanup state
