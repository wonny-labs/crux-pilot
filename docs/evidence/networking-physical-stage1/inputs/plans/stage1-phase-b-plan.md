## 1. Purpose, scope, what it proves

| Item | Content |
| --- | --- |
| Purpose | Stage 1: show that Ethernet works on the current bench (board, dedicated cable, AX88179 `en13`), as the base for the later HTTPS/SSH/SFTP stages. |

| Does NOT prove | HTTPS, SSH, SFTP, entropy, persistence or timing of the management stack; link loss and recovery; three-boot repeatability; worst-case timing or stack margins; anything about the integrated image of PR #313. |

## 5. Operations in order

Common rules. Environment for every command: `LC_ALL=C`, `TZ` and `COLUMNS` unset, and the Python of venv `.worktrees/stage1-ws/venv` (host prerequisite P2; the venv is outside the checkout so the clean-tree check and the guard's folder are untouched). All evidence directories are **direct children** of `RUN=.worktrees/stage1-ws/stage1-run/` (new, empty): `identify`, `program`, `boot-1` (the capture), `restore`; the lock `evkb-602003106.lock`, the `m5-driver-<mode>.consumed` markers, `m5-series-session.json` and `boot-1-safety/` therefore live together in `RUN`. Each command's console output (stdout, stderr and exit code) is saved next to its evidence directory (`RUN/<name>.console`), because a failure before the driver or the capture adapter is constructed leaves no JSON record. Each physical command is announced to the main session in one line when it happens. While a step runs, nothing else touches the J-Link files or runs a J-Link process (the ownership check refuses on any process whose arguments contain `JLink`, `openocd` or `pyocd`).

## 6. Stop conditions (any one ends all hardware changes; no retry beyond the plan; report)

Probe timeout or unknown exit; any identity mismatch (core, DPIDR, probe serial, VTref outside 3.0 to 3.6 V); unexpected firmware-maintenance text; the guard record missing, expired, rebooted-from, STOPPED, or its script hash changed; any UART owner other than the capture, or a debugger process; adapter MAC, address, service or route different; no carrier or no `LINK` up on the target after the M5 start (the Ethernet result then is FAIL, reported; no reset retry); a mount of the DAPLink volume appearing; image or manifest hash change; series budget exhausted; a verify mismatch; any exception of the driver or runner (a failed command is the last command). Records: after the driver has entered, `failure.json` is written; a failure while acquiring the UART, loading inputs or constructing the capture adapter leaves no JSON record and the series session file stays `RUNNING`, so the saved console output is the record and no retry is possible under the same `RUN`; any operation not in section 5. Recovery: the one-per-incident power cut `uhubctl -l 0-1.1 -p 4 -a off` (never another port), announced first, never during programming or capture, for: a stuck `umount`/`mount`, a hung board, the guard logging `FAILED` after B0, or an RT1060 volume appearing mounted after B0 (leaving it mounted is the hazard the guard exists for).

## 7. Restoration

B5 restores and fully verifies the accepted normal image (byte-identical to the accepted `ad729684...`); the plan ends with that image running. If B3 or B4 fails after the `program-m5` probe command has started (a timeout in the middle of `loadfile` leaves the flash state unknown; `restore` does not check the entry image, so it can run from that state), or B3b ends in FAIL or INCONCLUSIVE, B5 is run as the only follow-up if the probe identity, guard and ownership checks still pass; if they do not, nothing more is done and the state is reported as unknown. I will say plainly in the report whether the board is back in the accepted normal state and how it was verified.

## 9. Known limits of this plan

No driver, runner or guard code has run on a real board yet; the first real operation of each is part of this run, and each fails closed. The arm-mode guard path and whether macOS routes the replugged FSKit mount through the root approval callback are untested on a device. Real Commander output for a verify mismatch, whether `connect` halts a running core, and `loadfile` duration against the 30 s limit for 97,544 and 107,872 byte images are unknown. The entry image is assumed (B2 decides). pyserial must be downloaded and installed (P2, named above). CI of the final head: host, psa-crypto and links green, the zephyr jobs not complete at the time of writing; CI bears on merging, not on the safety of these operations. The `loadfile` duration is unknown: an earlier J-Link log in the repository (`microsd-physical/run1-flash-jlink.log`) shows 65,536 bytes taking 4.28 s in total, which suggests it fits the 30 s limit, but the SWD speed of that run is not recorded; a timeout is a stop condition.
