## Q1. eMMC boot partition model

| ID | Statement | Source | Label | Caveat |
|---|---|---|---|---|
| C-1 | Linux exposes the two boot partitions as `mmcblkXboot0` and `mmcblkXboot1`. It makes them read-only by default through `force_ro` to avoid accidental bricking, and write access is switched on by clearing that flag. This is a kernel-side software guard, not a card feature. | `LX/Documentation/driver-api/mmc/mmc-dev-parts.rst` L11-L31; code that creates the partitions with the read-only default: `LX/drivers/mmc/core/mmc.c` L458-L470 and L318-L326 | Verified by public vendor document | Kernel behaviour, not eMMC-spec text. The doc file is from Linux master at the commit above. |
| C-2 | The device has two boot regions of equal size. Each size is `BOOT_SIZE_MULT` (EXT_CSD byte 226) times 128 KiB. | `LX/drivers/mmc/core/mmc.c` L458-L470 (shift by 17); `MU/mmc_cmds.c` L1788 and L3782 (multiplies by 128 KiB) | Verified by public vendor document | I give no size for any device on purpose. |
| C-3 | RPMB is a third area besides the boot partitions and the user area. Linux sizes it from `RPMB_SIZE_MULT` (byte 168) shifted by 17, and `PARTITION_ACCESS` value 3 selects it. | `LX/drivers/mmc/core/mmc.c` L583; `LX/include/linux/mmc/mmc.h` L275 and L337-L340; `MU/mmc_cmds.c` L1876-L1900 (prints "R/W RPMB" for access value 3) | Verified by public vendor document | Authentication protocol of RPMB is out of scope here. |
| C-4 | `PARTITION_CONFIG` is EXT_CSD byte 179. Bit 6 is BOOT_ACK. Bits 5:3 are BOOT_PARTITION_ENABLE: 0 = not boot enabled, 1 = boot partition 1 (boot0), 2 = boot partition 2 (boot1), 7 = user area. Not read from the standard. Note the off-by-one naming: BOOT_PARTITION_ENABLE value 1 means the partition Linux calls boot0. |
| C-5 | `BOOT_BUS_CONDITIONS` is byte 177: boot mode (single backward-compatible, single high-speed, dual), whether the bus conditions reset after boot, and boot bus width. | `MU/mmc.c` L119-L124; `MU/mmc_cmds.c` L1912-L1913; `UB/doc/usage/cmd/mmc.rst` L123-L148; `UB/drivers/mmc/mmc_boot.c` L199-L206 | Verified by public vendor document | Which of these settings an SoC boot ROM can honour is SoC specific and out of scope. |
| C-6 | `BOOT_CONFIG_PROT` is byte 178 and exists next to byte 177 and 179. The tools only print it. EDK2 annotates it with two register access types ("R/W" and "R/W/CP"). | `MU/mmc_cmds.c` L1910-L1911; `https://github.com/tianocore/edk2/blob/b9d8871d3432048a47371e39f5b7413a40e4a774/MdePkg/Include/IndustryStandard/Emmc.h` L187-L189 | Not verified | What the bits protect (for example whether they lock `PARTITION_CONFIG` until power cycle or permanently) is spec text I did not read. No free source I read states it. |
| C-7 | `BOOT_WP` is byte 173. Bits as defined by Linux and mmc-utils: 0x01 power-on protect enable; 0x02 power-on partition select; 0x04 permanent protect enable; 0x08 permanent partition select; 0x10 permanent-protect disable; 0x40 power-on-protect disable; 0x80 partition-select enable. | `LX/include/linux/mmc/mmc.h` L275 and L332-L335; `MU/mmc.h` L118 and L196-L202; `UB/include/mmc.h` L226 and L309-L311 | Verified by public vendor document | Bit meanings are paraphrased. mmc-utils names the bits, for example `B_SEC_WP_SEL` for 0x80. Linux and U-Boot headers list only some of the bits. |
| C-8 | `BOOT_WP_STATUS` is byte 174, read-only. It carries two bits per boot area: 0 not protected, 1 power-on protected, 2 permanently protected, 3 reserved. | `UB/cmd/mmc.c` L108-L135; `UB/include/mmc.h` L227; `MU/mmc.h` L117 and L192-L195; `MU/mmc_cmds.c` L205-L243 | Verified by public vendor document | mmc-utils prints these fields only when the device reports EXT_CSD revision 5 or higher (`MU/mmc_cmds.c` L205-L208); which spec revision introduced them was not read. |
| C-9 | Software can set power-on write protection of the boot areas by writing `BOOT_WP` with the CMD6 switch command. Linux does this through the sysfs file `ro_lock_until_next_power_on`; U-Boot does it with `mmc wp`; mmc-utils with `writeprotect boot set`. The protection can be set for both partitions or for one chosen partition. | `LX/drivers/mmc/core/block.c` L253-L300 and L1141-L1152; `UB/drivers/mmc/mmc.c` L931-L960; `UB/doc/usage/cmd/mmc.rst` L121; `MU/mmc_cmds.c` L289-L368 | Verified by public vendor document | Linux shows the sysfs file only if the card reports the feature, and as read-only if the power-on-disable bit (0x40) is set (`LX/drivers/mmc/core/block.c` L340-L358; doc L33-L36). |
| C-10 | Permanent write protection of the boot areas is set the same way, with the permanent enable bit. The tools treat it as dangerous: Linux deliberately does not expose it through sysfs; mmc-utils offers it only in a build with a dangerous-commands flag and its help text calls it a one-time programmable, unreversible change. | `LX/Documentation/driver-api/mmc/mmc-dev-parts.rst` L38-L41; `MU/mmc.c` L61-L77; `MU/mmc_cmds.c` L289-L368 (permanent branch at L359-L360) | Verified by public vendor document | The help text is mmc-utils' wording. I did not read the standard's definition. |
| C-11 | What the states mean, from a vendor white paper: permanent protection cannot be disabled once enabled; power-on protection can be reversed only by a power cycle or by toggling the device reset pin; boot partitions can be permanently, secured or power-on write protected (temporary protection is not listed for them); read access stays possible on write-protected areas. | Western Digital white paper "e.MMC Security Methods", July 2017, section 2.2: `https://documents.westerndigital.com/content/dam/doc-library/en_us/assets/public/western-digital/collateral/white-paper/white-paper-emmc-security.pdf` (read 7 Nov 2026; full text extracted, 12 pages) | Verified by public vendor document | It describes eMMC 5.1. Vendor summary of the standard, not the standard. The cited text is in section 2.2, document page 5. |
| C-12 | Neither tool nor kernel code I read has a path that clears an enabled power-on or permanent boot write protection by software: the only writes to `BOOT_WP` set enable bits. Power-on protection ends with a power cycle or device reset (C-11). | Searched `LX/drivers/mmc/core/block.c`, `LX/drivers/mmc/core/mmc.c`, `MU/mmc_cmds.c`, `UB/drivers/mmc/mmc.c`, `UB/cmd/mmc.c`, `RA/src/emmc.c` for code that writes `BOOT_WP`; every hit ORs in an enable bit (cited at C-9, C-10) | Inference | From C-9, C-10, C-11. | C-13 | The ability to set protection can itself be switched off in the register: Linux and mmc-utils name a power-on-protect disable bit (0x40) and a permanent-protect disable bit (0x10), and mmc-utils prints "not possible" when they are set. | `LX/include/linux/mmc/mmc.h` L332-L335; `LX/drivers/mmc/core/block.c` L349-L356; `MU/mmc_cmds.c` L213-L225 | Verified by public vendor document | Whether those disable bits are one-time programmable is spec text I did not read (a mailing-list summary said the permanent-disable bit can turn the feature off, but I could not fetch the message). | C-14 | `RST_n_FUNCTION` (EXT_CSD byte 162) selects whether the hardware reset pin works: temporarily disabled, permanently enabled or permanently disabled. ## Q4. RT1060 ROM and eMMC, framing only

Public SPSDK material treats SD, MMC and eMMC as boot media with a bootable-image layout for the RT10xx family, and blhost has memory identifiers for uSDHC SD and MMC memory. I found nothing in the SPSDK and tool material that describes how the RT1060 ROM chooses between the eMMC boot partitions. The NXP reference manual was not read by this research. The record's author later read the manual's MMC boot details (evidence B, row B-84): the ROM reads `BOOT_PARTITION_ENABLE` and boots from the named boot partition or the user area. Fallback between boot partitions was not found.

| ID | Statement | Source | Label | Caveat |

## Expectations #299 can carry into #298 (all Inference, from the rows named)

1. Mechanically an eMMC offers two boot partitions and one selector byte, so a "write the inactive one, then switch" pattern exists in frameworks (C-17, C-21, C-25). RAUC says the switch is atomic and that this protects against a failure during the update. SWUpdate makes no atomicity statement. Neither states the power-fail behaviour of the image write.
2. That pattern requires the boot partitions not to be hardware write protected at update time. Power-on protection is set by software and cleared only by power cycle or reset; permanent protection ends any software update of that partition (C-9 to C-12, C-18).
3. Zephyr at the pin gives no API for boot partitions, boot configuration or protection (C-27 to C-33). Any use of them would be new code in the product configuration, probably through the host controller API (C-35) or a new narrow interface, and is an architecture decision for a later task.
4. Evidence B row B-84 (RT1060 manual) says the ROM reads `BOOT_PARTITION_ENABLE` and boots from that boot partition or the user area. What it does when a boot partition is damaged, and whether it falls back to the other one, is not found (C-39 to C-44), so #298 must settle that from the reference manual or hardware evidence before an A/B bootloader or a protection policy is assumed.
5. Product-policy choices that live outside firmware: permanent protection, `RST_n` configuration, disable bits, the initial programming path and RMA handling (C-45 to C-50).
