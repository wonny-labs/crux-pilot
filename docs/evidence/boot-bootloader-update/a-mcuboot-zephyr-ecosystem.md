## 1. Question 1: can MCUboot update itself, or a bootloader region?

| ID | Statement | Source | Label | Caveat |
| --- | --- | --- | --- | --- |
| A-1 | No file under `docs/` or `boot/` at the MCUboot pin describes or implements a bootloader self-update, a "bootloader image" in the multi-image scheme, or a bootloader-upgrade option. Case-insensitive search patterns used: `bootloader (upgrade|update)`, `upgrad(e\|ing) the bootloader`, `update the bootloader`, `self.?upgrad`, `self.?updat`, `second stage`, `2nd stage`, `chain`, plus a search for every reference to `FLASH_AREA_BOOTLOADER` and `boot_partition`. The only hits are unrelated (image swap text, Espressif multi-image text, chain-loading of an application). | Whole-tree search of `mcuboot@ee39e2d` `docs/*.md`, `boot/**`. Closest hits: `docs/readme-espressif.md`:738-750, `docs/design.md`:375-405 and 951 | Verified on pinned source | Absence claim limited to `docs/` and `boot/` (other trees such as `sim/`, `scripts/`, `ci/` not searched). "Not found" is not a statement that no downstream fork adds it. |
| A-2 | The design document lists a flash-area ID `FLASH_AREA_BOOTLOADER 0` and says the bootloader area "contains the bootloader image itself". The stock Zephyr port never uses it: no file in `boot/bootutil/`, `boot/zephyr/` or `boot/boot_serial/` mentions `FLASH_AREA_BOOTLOADER`. It is defined only by the Cypress and Espressif ports (`boot/cypress/MCUBootApp/sysflash/sysflash.h`:8, `boot/espressif/include/sysflash/sysflash.h`:20) and in `docs/PORTING.md`:122. | `mcuboot@ee39e2d:docs/design.md#L178-L207`; `docs/PORTING.md#L112-L125`; `boot/espressif/port/esp_mcuboot.c#L73`; `boot/cypress/cy_flash_pal/cy_flash_map.c#L78` | Verified on pinned source | I did not read how the Cypress and Espressif ports use the entry (a flash-map table row only, as far as the greps show). The ID exists to describe the layout, not to give the loader a way to write it. |
| A-3 | The loader (swap, overwrite, direct-XIP, RAM load) opens only the primary and secondary slot of each image, and the scratch area only when swap-using-scratch is built. `boot_open_all_flash_areas()` loops over images and slots with `flash_area_id_from_multi_image_slot()` and opens `FLASH_AREA_IMAGE_SCRATCH` under `#if MCUBOOT_SWAP_USING_SCRATCH`. The direct-XIP and RAM-load `context_boot_go()` calls the same function. | `mcuboot@ee39e2d:boot/bootutil/src/bootutil_loader.c#L311-L352`; `boot/bootutil/src/loader.c#L1741-L1745` (swap path), `#L2393-L2400` (direct-XIP and RAM-load path) | Verified on pinned source | Single-slot and single-slot RAM-load builds use a different open routine (`boot/zephyr/single_loader.c`:119); it also opens only `FLASH_AREA_IMAGE_PRIMARY(0)`. |
| A-4 | In the Zephyr port the area IDs the loader can name are only partition IDs of `slotN_partition` (primary/secondary macros) and `scratch_partition`. `flash_area_id_from_multi_image_slot()` returns only those, or `-EINVAL`. | `mcuboot@ee39e2d:boot/zephyr/include/sysflash/sysflash.h#L14-L30`, `#L100-L110`; `boot/zephyr/flash_map_extended.c#L93-L112` | Verified on pinned source | A build-time hook (`CONFIG_BOOT_FLASH_AREA_HOOKS`, #141 row `B77`; the call is at `flash_map_extended.c`:98) can replace the mapping. The stock mapping does not include `boot_partition`. |
| A-5 | Why the `mcuboot` partition (128 KiB at offset 0 on the RT1060 qspi dts, #141 `A9`) is not reachable by the stock loader: it is not a slot, not scratch, and no stock code path names its partition ID. Swap, overwrite, direct-XIP and RAM-load all read, erase or write only the areas of A-3 (#141 `S2-4`, `S2-7`, `S2-8` for the write and erase sites). | Inference from A-2, A-3, A-4 and #141 `A9`, `S2-4`, `S2-7`, `S2-8` | Inference | Not a security property. It is the absence of a code path. A custom hook or board overlay could redirect a slot ID to any partition, including one that overlaps the running bootloader. |
| A-6 | Multi-image mode gives each updatable image its own slot pair (`slot0/slot1` for image 0, `slot2/slot3` for image 1, up to eight images). `MCUBOOT_IMAGE_NUMBER` is `CONFIG_UPDATEABLE_IMAGE_NUMBER`. The loader swaps all images but boots only image 0; the design document says the other images are "started by another image". | `mcuboot@ee39e2d:boot/zephyr/include/mcuboot_config/mcuboot_config.h#L122-L125`; `boot/zephyr/Kconfig#L1113-L1120`; `boot/zephyr/include/sysflash/sysflash.h#L21-L30`, `#L66-L98`; `docs/design.md#L939-L951`; `docs/readme-zephyr.md#L14-L30` | Verified on pinned source | The Espressif port documents the same split ("Host OS boots second image": the bootloader updates the second image but does not boot it), `docs/readme-espressif.md`:738-750. |
| A-7 | An MCUboot maintainer's own suggestion for "update the bootloader" is to keep MCUboot as a very light first stage and chain a second updatable image after it (MCUboot -> first image -> main image), using the multi-image feature. That is a design the project describes in prose, not a feature with a stock Kconfig or sysbuild mode. See A-33. | MCUboot issue #1403 (collaborator comment of 6 Jul 2022) | Verified by public vendor document | Maintainer comment in a closed issue, not release documentation. |
| A-8 | A bootloader image placed as multi-image image N would be swapped into a primary slot while the first-stage code runs in place from the same NOR. That has the same write-while-executing hazard as #141 `R2`/`S2-4`, now applied to the code that is doing the swap. Whether MCUboot would refuse a slot that overlaps the executing bootloader was not checked. | Inference from A-3, A-6, #141 `S2-4`, `R2` | Inference | No overlap check was searched for. Treat "no check" as Not verified, not as a finding. |
| A-9 | Firmware-loader ("firmware updater") mode is not a bootloader updater. MCUboot keeps one application slot; the secondary slot holds a separate loader application, signed with the same key, that runs on a GPIO, a reset-pin or boot-mode request, or when no application is bootable. That loader's job is to update the application in slot 0. `slot1_partition` is its code partition. | `mcuboot@ee39e2d:boot/zephyr/Kconfig#L654-L664`; `boot/zephyr/firmware_loader.c#L162-L207`; `boot/zephyr/Kconfig.firmware_loader`; `zephyr@684c9e8:modules/Kconfig.mcuboot#L328-L335`, `#L382-L390`; `share/sysbuild/image_configurations/BOOTLOADER_image_default.cmake#L34-L43` | Verified on pinned source | Release notes line 353-357 confirm the purpose. This mode removes the revert-capable second application slot, so it is a recovery/loader design, not an extra fallback (see #141 A3, B10, B78). |
| A-10 | Serial recovery and mcumgr upload through MCUboot can only target slot areas. `bs_slot_info` and the upload handler open `flash_area_id_from_multi_image_slot(img_num, 0)` (or, with direct-image upload, `flash_area_id_from_direct_image()`, which returns `slot0_partition` ... `slotN_partition`). | `mcuboot@ee39e2d:boot/boot_serial/src/boot_serial.c#L745-L755`, `#L970-L983`; `boot/zephyr/flash_map_extended.c#L134-L170` | Verified on pinned source | The `boot_serial_uploaded_hook` (line 1176) lets a custom build see an upload; I did not read it as a way to redirect writes. |

## 3. Question 3: what happens when the bootloader is bad, or every slot is bad

| ID | Statement | Source | Label | Caveat |
| --- | --- | --- | --- | --- |
| A-20 | MCUboot does not validate the bootloader itself. Its image validation (header, hash, signature, TLVs, security counter) is run on slot images only, and no routine in the files searched reads, hashes or verifies the `boot_partition`. | Absence over `mcuboot@ee39e2d:boot/bootutil/src/*.c` and `boot/zephyr/*.c` (no use of `boot_partition` or `FLASH_AREA_BOOTLOADER`, A-2). Validation sites: `loader.c#L1924-L1934`, `#L1938-L1946` | Verified on pinned source | Self-evident but stated because the claim needs an absence search: the code that would verify the bootloader would have to run before the bootloader. That job belongs to the boot ROM or an earlier stage, never to MCUboot. |
| A-21 | If the loader cannot open its flash areas it halts: `context_boot_go()` calls `FIH_PANIC` on `boot_open_all_flash_areas()` failure. | `mcuboot@ee39e2d:boot/bootutil/src/loader.c#L1741-L1745` | Verified on pinned source | The direct-XIP and RAM-load variant instead sets the failure result and goes to `out` (`#L2398-L2402`). |
| A-22 | If no slot image can be booted, `boot_go()` returns a non-success value and `main()` logs "Unable to find bootable image", reports `NO_BOOTABLE_IMAGE_FOUND` and then calls `FIH_PANIC`. In swap mode a primary slot image that fails validation after the update step, or lacks the image magic, makes `context_boot_go()` return failure without erasing it (#141 `S2-7`). In direct-XIP and RAM-load an invalid image is erased and the other slot tried (#141 `B65`), and if neither is valid the same failure path is taken. | `mcuboot@ee39e2d:boot/zephyr/main.c#L628-L632`, `#L656-L678`; `boot/bootutil/src/loader.c#L1924-L1946` | Verified on pinned source | Whether a Crux build reaches this path was not run. |
| A-23 | `FIH_PANIC` is an endless loop. With fault-injection hardening off (the default profile), it is `while (1) {}`. With the low, medium or high profile, it is `fih_panic_loop()`, a run of branch-to-self instructions followed by `while (1)`. After a successful hand-off that returns, `main()` also ends in `while (1)` ("Never should get here"). | `mcuboot@ee39e2d:boot/bootutil/include/bootutil/fault_injection_hardening.h#L59-L80`, `#L139-L145`; `boot/bootutil/src/fault_injection_hardening.c#L67-L83`; `boot/zephyr/Kconfig#L968-L1003`; `boot/zephyr/main.c#L705-L707` | Verified on pinned source | The loop does not reset. Whether an installed watchdog resets the device out of it is A-24. |
| A-24 | A watchdog can turn the panic loop into a reset loop, but only if one is enabled. MCUboot installs a watchdog timeout at boot when `CONFIG_WATCHDOG` is on (setup default y, install default y, timeout default 300000 ms) and feeds it at the start and during swap and copy operations. `FIH_PANIC` feeds nothing. | `mcuboot@ee39e2d:boot/zephyr/main.c#L529-L530`; `boot/zephyr/Kconfig#L1344-L1386` | Inference | From the Kconfig defaults and from A-23 (no feed in the panic loop). Not checked: whether a WDOG driver is enabled in a Crux MCUboot build, whether the RT1060 watchdog survives into the application and what the reset does to the NOR (FlexSPI state after reset is a boot ROM matter). |
| A-25 | Stock options exist to stay in a recovery mode instead of looping when no application boots: `BOOT_SERIAL_NO_APPLICATION` (serial recovery), `BOOT_USB_DFU_NO_APPLICATION` (USB DFU) and `BOOT_FIRMWARE_LOADER_NO_APPLICATION` (loader slot). All are off by default. | `mcuboot@ee39e2d:boot/zephyr/main.c#L658-L677`; `boot/zephyr/Kconfig.serial_recovery#L176-L180`; `boot/zephyr/Kconfig.firmware_loader`; `boot/zephyr/firmware_loader.c#L197-L205` | Verified on pinned source | These recover from a bad application, not from a bad bootloader. They are not on the RT1060 board file path (#141 `B8`). |
| A-26 | Field behaviour when the bootloader code itself is corrupt (bad FCB, IVT, DCD or code in `boot_partition`) is decided by the SoC boot ROM and the board strap, not by anything in MCUboot or Zephyr at the pin. | Follows from A-20 and #141 `A7`, `B86`, `B87` | Not verified | The slice did not read the i.MX RT1060 reference manual. #141 already records recovery of a damaged bootloader through boot ROM paths as Not verified. |

## 4. Question 4: public designs for an updatable bootloader

### 4a. Nordic nRF Connect SDK: immutable NSIB (B0) plus upgradable MCUboot

| ID | Statement | Source | Label | Caveat |
| --- | --- | --- | --- | --- |
| A-27 | The SDK offers two chains. Single-stage: an immutable bootloader (NSIB or MCUboot) that updates only the application. Two-stage: NSIB as immutable first stage, MCUboot as upgradable second stage, which can update itself and the application. The docs recommend the second stage only when design or update needs require it, because a second bootloader adds attack surface. | `ncs@dc06430:doc/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader.rst#L10-L18`, `#L51-L68`, `#L127-L144` | Verified by public vendor document | Read in full (raw RST). Paraphrased. |
| A-28 | What is immutable: NSIB. After each reset it locks the flash range holding itself and its configuration with the chip's write-protection hardware; the doc says it cannot be modified or deleted without erasing the whole device. What is updatable: the second stage (MCUboot), which NSIB verifies, selects and boots, and the application. The doc names the write protection driver (`fprotect`) as using ACL, BPROT, RRAMC or SPU depending on the chip, with protection irreversible until reset. | `ncs@dc06430:doc/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader.rst#L92-L97`; `samples/bootloader/README.rst#L33`; `doc/nrf/libraries/security/bootloader/fprotect.rst#L9-L12` | Verified by public vendor document | The immutability is a runtime lock set by NSIB after reset, which relies on NSIB's own code running first from an unmodifiable place. The sources read do not state what makes the first fetch of NSIB code trustworthy on each chip (for example boot ROM). |
| A-29 | Hardware relied on: flash write protection (above); a provisioning area holding public-key hashes, a version counter and invalidation tokens, kept in the one-time-programmable UICR region on nRF91 and nRF5340 and in internal flash otherwise (the bootloader blocks writes before booting the next image); on nRF54L the KMU holds the keys and revocation policy. UICR on nRF91 and nRF5340 can be erased only by erasing the whole flash. | `ncs@dc06430:samples/bootloader/README.rst#L35-L39`, `#L64-L85`; `doc/nrf/libraries/security/bootloader/bl_storage.rst#L10-L27`; `doc/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader_signature_keys.rst#L127-L139` | Verified by public vendor document | Chip specifics do not carry over to the i.MX RT1060. They show the pattern: an immutable stage plus write lock plus a small non-erasable store. |
| A-30 | Slots: NSIB has two alternate slots `s0_partition` and `s1_partition` for the next stage. It boots the valid slot with the newest version; a new second stage is written to the slot with the oldest version; if that image is faulty, the other slot still holds a working image that is booted. MCUboot lives in `s0_partition`/`s1_partition` and is linked to its slot with `zephyr,code-partition`; sysbuild builds a separate "S1 variant" image linked for the other slot. The update package for the second stage must contain images for both slots, because the slot in use may be unknown in the field. | `ncs@dc06430:samples/bootloader/README.rst#L98-L136`; `doc/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader_partitioning.rst#L108-L142`; `doc/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader.rst#L146-L162`; `bootloader_adding_sysbuild.rst#L338-L347` | Verified by public vendor document | The doc says the immutable bootloader is responsible for upgrading the upgradable bootloader and verifying it (`bootloader.rst`:135-137). The text read does not spell out which code writes the new image into the other slot, nor what happens if power fails while that write is in progress. See A-32. |
| A-31 | Versioning, counter and keys. ### 4b. Arm TF-M: immutable BL1 plus MCUboot-based BL2
