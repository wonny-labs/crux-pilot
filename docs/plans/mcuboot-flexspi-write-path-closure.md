## Summary

- **What the bootloader writes is small and known.** In RAM load with revert, MCUboot writes NOR in three situations only: one trailer flag, `copy_done`, when it first selects an image (one 1-byte write); a whole-slot erase when the selected image has no good trailer magic or was started and never confirmed; and a whole-slot erase when an image fails to load or to validate. There is no swap, no status write and no other write in this mode (section 2). A slot is 3 MiB, which the erase loop clears one 4 KiB sector at a time, so a slot erase is 768 erase calls, each with its own busy poll (**Inference** for the 4 KiB unit).
- **The demonstrated failure has a one-line shape on the pinned source.** The busy poll reads the FlexSPI register base through a pointer to a `const` object that lives in NOR (`memc_flexspi_config_0`). Zephyr v4.4.2 already relocates the sibling xSPI driver's text **and** read-only data into the XIP memory (`drivers/memc/CMakeLists.txt` lines 9 to 12), and relocates only the text of the FlexSPI driver (lines 5 to 7). The three source files that the #22 PoC pinned are byte-identical at v4.4.2 (section 1).
- **Recommendation (decision D1): a bounded work package that does two board-free things, then lets the bench run under a staged, recoverable policy.** (1) A Crux composition fragment that relocates only the FlexSPI configuration object into the XIP memory (ITCM) for the MCUboot image, no change to Zephyr or MCUboot. (2) A host and CI check that reads the built MCUboot ELF and fails if any function reachable from the NOR write and erase entry points calls into NOR, loads a NOR address from its literal pool, or reaches a device record whose configuration pointer lies in NOR. Neither closes the full #22 matrix. They remove the one demonstrated edge, and they make every further edge visible without hardware. A small upstream Zephyr patch is the alternative to (1) and the better long-term home (decision D3).
- **No physical result closes this item.** #22 states that a passing run cannot qualify a busy interval. Physical evidence is a bounded, recorded observation under a stated policy, in a block of the combined bench runbook (section 5). Any claim of full closure stays **Not verified**.
- **#165 under-describes the first bench exposure.** Every MCUboot boot runs the FlexSPI driver's probe from NOR, and #22 lists startup as an open phase too. That happens on T1 even for a case that writes nothing (section 3).
- **Decisions needed:** D1 approve the work package and its order; D2 approve a new opt-in Crux Kconfig symbol and the edit of the module's `zephyr/Kconfig` and `zephyr/CMakeLists.txt` that carries it; D3 approve preparing an upstream Zephyr patch; D4 the bench policy until the check exists; D5 accept the residual risk that this does not remove, by name (section 7).

## 2. What MCUboot writes to NOR (question a)

Mode: RAM load with revert (`SB_CONFIG_MCUBOOT_MODE_RAM_LOAD_WITH_REVERT`), which defines `MCUBOOT_RAM_LOAD` and `MCUBOOT_RAM_LOAD_REVERT` (`boot/zephyr/include/mcuboot_config/mcuboot_config.h` lines 108 to 113). Pinned MCUboot v2.4.0, `boot/bootutil/src/` unless a path says otherwise. The resolved `.config` of the build was not read: where a row depends on an option, the option is named.

| # | Trigger | Write | Call chain | Extent | Label |
| --- | --- | --- | --- | --- | --- |
| W1 | First selection of an image that has `BOOT_MAGIC_GOOD` and `copy_done` unset (a padded, confirmed image has `image_ok` set, so this is its only write) | `copy_done`, written **before** the image is validated | `boot_load_and_validate_images()` (loader.c, call at 2295) → `boot_select_or_erase()` (2181 to 2235, write at 2224) → `boot_write_copy_done()` (bootutil_public.c 495 to 504) → `boot_write_trailer_flag()` (377) → `boot_write_trailer()` (345 to 374) → `flash_area_write()` | One aligned write of `ALIGN_UP(1, write-block)` bytes. With `write-block-size = <0x1>` (Stage 6, Verified in repository) that is 1 byte, so one NOR page program of 1 byte. A failed write is logged and boot continues | Verified on pinned source. Size: **Inference** |
| W2 | The selected image has no `BOOT_MAGIC_GOOD`, or has `copy_done` set and `image_ok` unset (an image that was started and not confirmed: the "revert") | Erase of the **whole slot**, from offset 0 upward | `boot_select_or_erase()` (loader.c 2199 to 2212) → `boot_scramble_region(fap, 0, flash_area_get_size(fap), false)` → `boot_erase_region()` (bootutil_area.c 195 to 292) → `flash_area_get_sector()` then `flash_area_erase()` per sector | 3 MiB slot, one `flash_area_erase()` per page the driver reports (4 KiB, fact 1.7), so 768 calls. Each call is a NOR sector erase with its own write-enable, busy poll and controller reset. The loop calls `MCUBOOT_WATCHDOG_FEED()` between calls | Verified on pinned source. Unit and count: **Inference** (fact 1.7). The slot size 3 MiB is a [provisional value](../boot-composition.md) |
| W3 | The image cannot be loaded to RAM | Erase of the whole slot | `boot_load_and_validate_images()` (loader.c 2310 to 2315) → `boot_remove_image_from_flash()` (ram_load.c 411 to 421) → `boot_scramble_slot()` (bootutil_area.c 364 to 395) → `boot_scramble_region()` | As W2 | Verified on pinned source |
| W4 | The image fails validation (signature, hash, header), in **either** slot | Erase of the whole slot | `boot_validate_slot()` (loader.c 640 to 662, the test at 652): `(slot != BOOT_SLOT_PRIMARY) \|\| ARE_SLOTS_EQUIVALENT()`, where `ARE_SLOTS_EQUIVALENT()` is 1 under `MCUBOOT_RAM_LOAD` (bootutil_priv.h 190 to 193) → `boot_scramble_slot()` | As W2 | Verified on pinned source |

What is **not** written, from the same sources:

- No swap, no status write, no swap-info and no magic write: the swap code is compiled out under `MCUBOOT_RAM_LOAD` (loader.c: the guards at 164, 365 to 367 with `boot_write_status` at 414, 462 to 493, 718 and 753, the last one running to the `#else` at 2056, which holds `boot_copy_region`, the swap erases and `boot_write_magic`). **Verified on pinned source.**
- No flash write in `boot/zephyr/main.c`: no `boot_write`, `flash_area_write` or `flash_area_erase` call in the file. The boot information goes to retained RAM. **Verified on pinned source.**
- `boot_validate_slot()` has one more erase, at loader.c line 707 (block 662 to 712), under `MCUBOOT_VERIFY_IMG_ADDRESS` or `MCUBOOT_CHECK_HEADER_LOAD_ADDRESS`, for an image in the secondary slot whose address is outside the primary slot. Neither is set in [`mcuboot.conf`](../../zephyr/boot/boards/mimxrt1060_evk_mimxrt1062_qspi_B/mcuboot.conf); whether the resolved configuration sets one is **Not verified**.
- A hardware security-counter update (`boot_update_hw_rollback_protection()`, loader.c 2347 to 2390) is compiled in only with `MCUBOOT_HW_ROLLBACK_PROT`. Whether the resolved configuration sets it is **Not verified**; the composition fragments do not (Verified in repository: [`mcuboot.conf`](../../zephyr/boot/boards/mimxrt1060_evk_mimxrt1062_qspi_B/mcuboot.conf)), and its store is not NOR in any case (**Inference**).
- Confirm (`image_ok`) and the staging writes are the **application's**: they run from SDRAM under the #22 matrix for the application, not in this item ([update agent design](update-agent-design-proposal.md)).
- With `CONFIG_MCUBOOT_STORAGE_MINIMAL_SCRAMBLE` (experimental, default off; Kconfig line 1325), W3 and W4 erase only the header sector and the trailer sectors. It does **not** shorten W2: `boot_select_or_erase()` calls `boot_scramble_region()` for the whole slot directly (loader.c 2209). **Verified on pinned source.**
- Plain RAM load (`SB_CONFIG_MCUBOOT_MODE_RAM_LOAD`) does not define `MCUBOOT_RAM_LOAD_REVERT`, so `boot_select_or_erase()` is compiled out (loader.c line 2169 guard), and W1 and W2 do not exist; W3 and W4 remain. **Verified on pinned source** for the code; that the sysbuild mode produces that define is **Inference** (sysbuild `Kconfig` lines 106 to 136, `modules/Kconfig.mcuboot` lines 258 to 270). The plan has not adopted either mode ([boot composition](../boot-composition.md)).

## 5. What evidence closes it (question d)

#22 sets the bar that a clean run is not closure. This section therefore splits **static and host evidence**, which can show a defect or the absence of the specific defect it looks for, from **physical evidence**, which records an observation under a policy.

### 5.1 Host and static evidence (can run in CI)

All of the following read the **built MCUboot ELF** of the documented composition, which `scripts/test-boot-composition.sh` already produces in the `runtime` shard of `zephyr.yml` (Verified in repository). They need the Zephyr SDK's `arm-zephyr-eabi-readelf`, `-nm` and `-objdump`, which the Dev Container has (Verified in repository: the WP1a record). No board is used.

| # | Check | Design | Fails when |
| --- | --- | --- | --- |
| S1 | Placement | `nm -n` and `readelf -lW` give the section and the run address of `memc_flexspi_config_0`, `flash_flexspi_nor_write`, `flash_flexspi_nor_erase`, `flash_flexspi_nor_wait_bus_busy`, `flash_flexspi_nor_read_status`, `memc_flexspi_transfer`, `memc_flexspi_reset`, `FLEXSPI_TransferBlocking` and the HAL functions they call | A function is outside the ITCM run range, or the configuration object's **run** address is inside the NOR window `0x60000000` to `0x60800000`. The existing [PoC checker](../../scripts/verify-flash-poc.py) is the model: ELF32 symbols with ITCM bounds |
| S2 | Reachability closure | From the roots of S1, follow direct `bl` and `b` edges in `objdump -d`. For every function reached, record each call target and each literal-pool load (`ldr rN, [pc, #imm]`) with the literal's value read from the ELF's file-backed bytes. Classify each value: ITCM, DTCM, OCRAM, SDRAM, peripheral, **NOR**, unknown | A reached function lies in NOR; a literal in NOR is not on a short, reviewed allow-list; an indirect branch (`blx rN`, `bx rN` that is not a return) has no resolved target. Indirect edges are **reported**, not silently skipped |
| S3 | Device-record pointer chain | Find the FlexSPI controller `struct device` record (`__device_dts_ord_<N>`, from `nm`) and read its `config` field from the ELF; do the same for the NOR driver's own device record. This is the manual step that produced Stage 6's finding. The field offset depends on the `struct device` layout of the pinned Zephyr, so the check asserts the layout it expects (the pin) and fails on a change | The controller's `config` target is in NOR |
| S4 | Source pin guard | Compare the SHA-256 of the three upstream files with the values of fact 1.1, in the checked-out Zephyr and HAL | A hash differs, so the analysis above no longer describes the code (the same guard the PoC generator uses) |
| S5 | Vectors and handlers (report only) | Print the section of the vector table, `z_arm_nmi` and `z_arm_fault`. Today they are in NOR in both builds (Stage 6) | No failure: this row cannot be closed by a mechanical rule, only by policy (section 7) |

Limits, stated so they are not forgotten: S2 sees code and constants, not run-time state (a pointer filled in at run time, such as the RAM copy of the controller, is covered only by S3's reading of its source record); it does not see stack contents or what the boot ROM left running; and a clean S1 to S4 shows the **absence of the edges these checks look for**, which #22 says is not closure. Each is host-testable with fixture disassembly text and a tiny synthetic ELF, as `tests/build/` does for the existing checkers, so a test-first implementation needs no board and no Docker for its logic. The new script would live in `scripts/`, a protected path (adding a **new** check script is allowed within an approved task; the CI wiring in `.github/workflows/zephyr.yml` and `scripts/test-boot-composition.sh` is a protected-path edit that needs its own explicit approval). Cost: 2 to 3 days with review, **Estimate**.

### 5.2 Physical evidence (a block for the combined bench runbook)

Proposed as a block of the [board test procedure](../secure-boot-board-test-procedure.md). It adds no step to that procedure by itself. It orders the cases that already write NOR so that exposure rises one step at a time, and it names what to record for #165. The approvals of section 2 of that procedure apply to each step, and a decision on #165 must be in the task record before T1.

## 7. Recommendation and decisions (question e)

**Recommendation.** Approve the bounded work package of option A plus the static checks S1 to S4 (decision D1), and prepare option B in parallel as the durable fix (D3). Hold the first physical step until the checks pass on the built ELF, then run the staged block of section 5.2 beginning with a case that writes nothing (D4). Do not start option C now. Do not call the item closed on any single result: close #165 only with the statement of what is covered.

**Reason.** It is the only combination that removes the one demonstrated mechanism, produces evidence that can be re-run in CI without a board, and measures how many other edges exist, all before hardware. It keeps the owner's instruction for the most board-free development. It also keeps the recoverable hardware experiment as the natural next step instead of a gamble: the hardware cases stay exactly those of the existing procedure, in an order that raises exposure one step at a time.

**Alternative.** Option D with option E: run T1 with plain RAM load now, accept the finding open as the procedure allows, and add A later. It is faster by about four days (**Estimate**) and buys the same startup evidence. It risks a stall or a fault at the first erase with no change made against the known cause, and it makes the demonstrated edge the first thing the board tests. I recommend it only if the owner puts the first board run ahead of the static work.
